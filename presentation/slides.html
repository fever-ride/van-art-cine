Part 2 · Architecture

Data Pipeline

1
Collect
Scrapes each cinema site and extract screenings into structured JSON.
Challenges
Finding elements we want and using selectors to extract data
Inconsistent HTML across sites
Solution
Headless Playwright with per-site parsers
Tools
Playwright, Python
→
2
Normalise & Stage
Unify time and title formatting. Written to staging table for safe re-runs.
Challenges
Noisy titles (Q&A, 4K, guests)
Safe re-runs without duplicating rows
Solution
Regex and rules
LLM integration for noisy titles
Staging table keyed by content hash
Tools
Regex, OpenAI GPT
→
3
Enrich
Resolve IMDb / TMDB IDs as stable keys, then enrich rows with poster, ratings, credits, and metadata from external APIs.
Challenges
Dependence on third-party APIs: rate limits, errors, and inconsistent availability
Identity resolution: same title can map to multiple candidates or none
Solution
Skip failures without blocking the run
Surface outcomes for observability
Throttle requests to respect provider limits
External APIs
TMDB API, OMDB API
→
4
Deduplicate
Group duplicate film and person rows by external ID.
Challenges
Same logical film or person ingested multiple ways; broken FKs if rows are deleted naively.
Solution
Group by IMDb / TMDB ID
Completeness scoring
Foreign key re-pointing
Applies to
Films table, People table
→
5
Publish
Promote staging into the live screenings table.
Challenges
A failed step must not leave the database half-updated
Showtimes from an older scrape may vanish from the latest feed
Inactive screenings should not be deleted
Solution
Promote in single transaction to ensure atomicity
Insert and update rows by stable identity keys
When automated ingest rows disappear from staging, soft-deactivate them instead of deleting rows outright
Target
PostgreSQL live screenings table
Part 2 · Architecture

Data model · Backend · Frontend

Data models

Core

app_user: User accounts, authentication info, and related records.

cinema: Cinema metadata such as name, website, and address.

film: Film titles and enriched metadata (ratings, cast, external IDs).

person: People associated with films (directors, writers, cast).

film_person: Join table linking films and people with a role.

screening: Final normalized showtimes linked to film + cinema.

watchlist_screening: Records of screenings saved by users.

refresh_token: Session storage and token rotation.

Ingestion

raw_import: One row per scrape/fetch.

stg_screening: Staging area for processed screening data before merge to live.

ops_ingest_run: Metadata for each ingestion pipeline run (counts, status, timing).

Backend: Node.js + Express + PostgreSQL + Prisma ORM

REST API: We expose route groups for auth, films, screenings, watchlist, cinemas, and user (profile / account).
MVC layers: routes → controllers → services → models.
Dual-token JWT: Short-lived access token + long-lived refresh token.
Middleware pipeline (Express): Use Express middleware as a policy layer to handle cookies, request validation, rate limiting, and centralized error handlings.
Guest vs signed-in user
Challenge
Users should be able to use the watchlist without logging in
But logged-in users need persistent, server-side data
Solution
Single UI flow: try API first; on 401, gracefully fall back to guest mode (localStorage)
After login, merge guest data into the account to keep a seamless experience

Frontend: Next.js + React + Tailwind

Page composition: Reuse shared UI primitives and higher-level feature components; pages are composed from these layers.
State without Redux: Separate hooks for UI state, data loading, and watchlist.
App Router: File-based routing where each folder under app/ represents a route segment, keeping the project structure clean and removing the need to define routes manually.
Rendering strategy: Use server components for SSR and keep client components only where interactivity is needed.
